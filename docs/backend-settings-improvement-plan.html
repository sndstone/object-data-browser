C01 · Implemented follow-upListing cancellation

Cancel now stops a stalled listing promptly

Previously, Cancel waited for the active request to finish. The local app change now releases the UI immediately, preserves completed results and ignores late data or errors. Desktop listing processes are stopped without interrupting transfer workers. Version/inspector reads in the listing workflow also participate.

Verified with hung-request fixtures and a real Cancel-button widget test: Flutter analysis is clean; 156 tests passed, 2 skipped. This is a source change, not a new installed release. Native SDK requests may still finish in the background. Implementation and verification details.

01 / Product direction

Keep the foundation. Remove the ambiguity.

2.2.6 already solved many basic GUI problems. The next pass should improve information hierarchy and connect the visible controls to real behavior.

Already good — preserve it

  • Lazy section navigation, profile drafts, masked secrets and 30-second reveal timeout.
  • Field validation, adaptive layouts, bundled fonts and independent density/text size.
  • Consolidated secure credential storage and atomic metadata backups.
  • Bounded sidecar pools, deadlines, typed errors and capability-gated transfer controls.
  • Per-file upload sizing, parent batch progress and bounded part workers.
  • Bounded previews, selectable source and static HTML rendering.

Change the settings structure

  • One heading per section, one clear explanation, less nested card padding.
  • Six stable categories, with advanced controls nested under the task they affect.
  • A compact connection list and one editor; always put “New connection” near the heading.
  • Separate “Test draft”, “Save connection” and “Connect”. Keep test results inline.
  • Show effective transfer settings, inheritance and engine support.
  • Keep preferences auto-saving, but acknowledge actual persistence results.

8 findings
P0B01Reproduced

Go Azure move can delete a source before its copy completes

The copy loop stops after 20 polls at 250 ms. Only failed and aborted are rejected; pending falls through to success. Move then deletes the source.

Evidence A loopback Azure fixture returned pending on every response. The freshly built Go engine made 20 HEAD requests, sent DELETE for the source, and returned ok: true. This reproduces the control-flow defect; no real Azure data was used.
Implementation, scope & acceptance checks
Change
Require an explicit success for the matching copy ID before source deletion. Return a typed pending/unknown outcome at the deadline, retain source identity and expose “Check copy status”. Treat missing status as unconfirmed. A move must record copy-complete and source-delete as separate phases; reconcile uncertain deletion instead of replaying the whole move.
Scope
Go first; then the Python Azure implementation and shared move-result semantics. Python currently rejects a still-pending status, but both paths should require affirmative, matching completion.
Acceptance
Fixture pending forever → zero source DELETEs. Also cover pending→success, failed, aborted, missing status, changed copy ID, a poll timeout, and source-delete failure after successful copy.
Effort
S · fix first, before another Azure-capable release

P0B02Reproduced

Downloads need collision handling and atomic destination writes

Python, Go and Rust derive the destination from the key’s basename and create/truncate the final file. Java also resolves basenames and writes multipart data into the destination. Prefix identity is lost.

Evidence Python downloaded a/report.txt and b/report.txt as one report.txt containing only SECOND, while the job reported completed. A forced GET failure also reduced a pre-existing local file to zero bytes. Equivalent destination patterns were found in the other desktop engines; their behavior was not executed in this check.
Implementation, scope & acceptance checks
Change
Build a download manifest before writing: object identity → validated relative destination. Default to preserving selected-prefix structure; offer Ask / Keep both / Skip / Replace for conflicts. Use exclusive, same-directory temporary files; verify and flush before publishing the final file. Handle case-insensitive collisions, Windows reserved names, dot segments and symlink escapes. Do not concatenate untrusted keys directly into paths.
Scope
Versioned download request with resolved paths and conflict policy across desktop and mobile. Reject unsupported policy fields on older engines rather than silently flattening names.
Acceptance
Same basename in two prefixes; existing local file; empty object; disk full; mid-stream failure; cancel; process exit; invalid names; case collisions; attempted path escape. No unapproved overwrite; failed downloads leave the original untouched.
Effort
M–L · UI preview and contract work required

P1B03Reproduced

Validate downloaded ranges and pin a consistent object identity

The Python S3 range worker reads the body, writes it, and returns the requested byte count without checking its actual length. Desktop range requests also omit version/ETag conditions in the reviewed download paths.

Evidence A controlled Python client supplied 3 bytes for a requested 1 MiB range. The job reported completed and 1,048,576 transferred bytes; the pre-sized output contained 3 payload bytes plus zero padding. Go and Java already check short range length; preserve that behavior. Mixed-version downloads are a source-level risk, not a reproduced provider incident.
Implementation, scope & acceptance checks
Change
Check actual bytes and response range semantics; count only bytes written. HEAD once for an object identity, then use the same version ID or If-Match condition for every GET. Fail with object_conflict on an identity change and keep the final destination untouched. Check available checksums without treating every ETag as a content hash.
Scope
Immediate Python repair; shared download identity and validation contract across adapters. Build on B02 temporary files.
Acceptance
Short/oversized range, ignored Range response, wrong offset, zero bytes, object replaced between ranges, 412, missing conditional support. All invalid reads fail rather than publishing a completed file.
Effort
M · short-read fix is smaller than identity parity
main.py:2937 · main.go:1638 · Main.java:1432 · S3 GetObject conditions and versions
P1B04Source confirmed

Make settings describe the effective transfer policy

The “Concurrent transfers” value is copied into the benchmark draft, but ordinary upload/download envelopes do not carry it. Desktop workers use profile pool limits capped at eight. Several global safety controls are serialized without runtime consumers.

Evidence Repository-wide use tracing found no runtime reads of global retryBaseDelayMs, retryMaxDelayMs, requestDelayMs, maxRequestsPerSecond or enableCrashRecovery beyond model/settings persistence. Global safeRetries, timeouts and maxPoolConnections feed benchmark configuration; browser operations serialize the profile’s separate values. Existing engine retries and host recovery still exist independently.
Implementation, scope & acceptance checks
Change
Define one validated effective policy with explicit scope: application default → optional profile override → immutable job snapshot. Distinguish queued files, active jobs, part workers and HTTP pool connections. Either wire each control end to end or hide it with a migration note. Show effective limits and capability-based availability. Specify retries versus total attempts, backoff bounds and safe operation classes; never automatically replay an unknown mutation.
Scope
AppSettings, profile schema, controller, engine request/descriptor contract and all adapters. Preserve sequential files inside one upload batch and bounded parallel part workers.
Acceptance
Change a setting and assert outgoing envelopes plus measured worker/retry behavior. Cross-engine fixtures cover zero retries, throttling, timeouts, incompatible engines and profile overrides. Prove cosmetic settings cannot affect the policy.

P1B08Source confirmed

Make legal multipart sizes safe for the runtime and memory budget

Settings permits a 5,120 MiB manual chunk. Java startDownload multiplies MiB into an int; 2,048 MiB overflows negative and 4,096 MiB becomes zero. Python upload workers materialize whole parts; automatic 128 MiB parts with eight workers imply roughly 1 GiB of payload buffers before SDK overhead.

Evidence The zero-byte chunk causes division by zero when calculating part counts; negative sizes also produce invalid range arithmetic. The range loop uses the same overflowed value. This was confirmed by inspecting arithmetic and boundaries; a multi-gigabyte transfer was not run. Actual memory usage was not profiled.
Implementation, scope & acceptance checks
Change
Use checked 64-bit arithmetic for byte offsets and sizes. Enforce limits at the engine boundary, including imported settings and direct contract callers. Stream large legal parts/ranges with bounded buffers; cap aggregate in-flight memory as well as worker count. Do not solve this by lowering S3’s supported object-size ceiling.
Scope
Java download arithmetic first; transfer planners and streaming implementations across engines. Preserve MultipartSizing’s S3 boundaries and per-file policy.
Acceptance
Boundary tests for 2,047 / 2,048 / 4,096 / 5,120 MiB using virtual sources, no enormous allocations. Invalid values fail before file mutation. Measure peak memory and cancellation under representative large transfers.
Effort
M for arithmetic · L for streaming and memory policy

04 / Features worth adding after the fixes

Useful extensions, with boundaries.

F01 · M–L

Version-specific download

The 2.2.6 ledger explicitly defers it because startDownload accepts keys without version IDs. Add object references with version identity, then show “Download this version” in the Versions inspector. Delete markers get no download action; unsupported engines get an explanation.

Depends on: B02/B03 and capability negotiation. Accept: two versions of one key download distinct bytes; retry preserves the requested version.

F02 · M

A useful connection check

Present separate connection/authentication and bucket-listing outcomes. Allow a known bucket/container check for restricted accounts. Explain which check failed, without treating inability to enumerate the account as proof that the endpoint is unusable.

Depends on: B06 draft testing and error mapping. Accept: a restricted fixture can pass its known-bucket check while account listing fails; testing never changes browser selection.

F03 · M

Engine compatibility at a glance

In Diagnostics, show effective engine/provider capabilities, runtime version, queue usage and available transfer controls. Link unsupported choices to a compatible installed engine. Rust/Java Azure support is absent today; do not silently switch engines or imply parity.

Depends on: a richer descriptor and B04. Accept: the screen matches each adapter’s advertised capabilities and handles unavailable engines honestly.

F04 · L · later

Recovery that reconciles uncertain outcomes

Add a credential-free journal of job intent and checkpoints. On restart, surface “Check outcome” for uncertain copy/move/upload operations, and verify remote identity before continuing. Redact sensitive signed URLs and never persist credential envelopes.

Depends on: B01–B04, identity-aware operations and retention rules. Accept: kill/restart fixtures never duplicate a destructive mutation. This is not a promise of byte-level resume across restarts.

Also useful: a “Follow system” theme option after replacing the current darkMode boolean with a migrated theme preference; and a field-level reset-to-default action that never resets credentials. Neither belongs ahead of the correctness work.

05 / Delivery plan

Ship in verifiable increments.

01

Protect data and report truth

B01 + immediate B02 protections + B03 short reads + B06 save outcomes + B07 cancel fix + B08 arithmetic.

Exit: pending copy never deletes its source; download failures preserve files; persistence failure cannot look saved.

02

Define effective behavior

B04 policy + B05 settings isolation + B02 destination contract + B03 identity + B08 streaming plan.

Exit: every displayed setting has a tested consumer and scope; incompatible engines fail explicitly.

03

Clean up settings

Six categories, connection editor, clear actions, search, transfer/location groups, responsive layouts and state migration.

Exit: no lost preferences or drafts; UI matches engine limits; keyboard and large-text checks pass.

04

Add targeted features

F01 version downloads, F02 connection checks and F03 compatibility diagnostics. Scope F04 separately.

Exit: capability tests and provider fixtures prove the new behavior before it becomes visible.

Architecture approach

Introduce small boundaries around the existing code: EffectiveTransferPolicy, DownloadPlan, typed SaveResult, connection drafts and a settings section registry. Extract profile/settings coordination and transfer planning from the 4,694-line AppController incrementally. Keep storage calls in engines.

The iOS and Android Dart service adapters are each 1,634 lines; assess a shared channel-envelope/codec layer after parity fixtures exist. Keep native platform capability differences explicit. Do not combine this cleanup with a backend rewrite.

Contract & rollout rules

Feature-detect added fields and capabilities. Bump the contract for breaking semantics; unknown download conflict or identity options must not be silently ignored. Snapshot effective settings when a job starts. Preserve all current Keychain migration/recovery boundaries, secret-free exports, static HTML previews and multipart limits.

Use narrow local changes and regression tests per finding. Public Apple packages retain Developer ID/provisioning/notarization requirements. Physical device Keychain/local-network checks remain required before an iOS release.
