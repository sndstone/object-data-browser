Recommended direction

The 2.2.5 pass fixed the big structural problems. What remains is a set of small trust gaps and rough edges that a user meets every day.

  • Close the destructive-action gaps first. Two delete paths and profile deletion still run without confirmation, and the banner cannot tell an error from a success.
  • Then remove duplication. Two search boxes, two settings navigators, three copies of byte/date formatting, a keyboard hint with no shortcut behind it.
  • Then finish the details. Type icons, real dates, copy buttons, dark-mode colors, semantics, empty states, bundled fonts.

What already works and should be preserved

Direction-aware motionWorkspace, mobile section and inspector transitions in DirectionalSwitcher respect reduced motion and the app preference. Keep as is.
Lazy object tableObjectTable uses fixed-extent rows, real checkboxes, shift-range selection and header sorting. Build on it; do not replace it.
Frame cachingBrowserWorkspaceFrame rebuilds the browser only when displayed data changes. New state added by this plan must be added to its signature.
Accessible select fieldAppSelectField has keyboard navigation, flip-up placement and a native fallback on touch. Reuse it everywhere a dropdown appears.
Text scaling modelPreferenceTextScaler never cancels OS enlargement, and row density is separate from text size. Any new dense layout must respect both.
Bounded previewsText and image previews stay bounded, HTML renders statically, source is highlighted and selectable. Untouched by this plan.

G01P0InspectorEffort S

Confirm before deleting from the Versions tab and the Delete-all tool

Observed: In browser_workspace.dart, the Versions tab button “Delete selected” calls controller.deleteSelectedObject directly, and the Tools tab button “Run delete all” calls controller.runDeleteAllTool directly. Neither shows a dialog. Delete-all removes every object in the bucket typed into the field. The object panel’s own Delete button does confirm (via _confirmDeleteObjects), so behavior is inconsistent between surfaces.

The edit
Route the Versions “Delete selected” through the existing _confirmDeleteObjects(context). Add _confirmDeleteAll(context) for the tool: a dialog that names the bucket, engine and batch size and requires the bucket name to be typed before the destructive button enables. Disable “Run delete all” while deleteAllState.running.
What it does
Makes every delete path in the app pass through one confirmation with the same wording, and makes the highest-impact action (whole-bucket deletion) require deliberate input.
How it functions
The dialog snapshots selectedProfile?.id and selectedBucket?.name the way _confirmDeleteObjects already does, so a profile switch during the dialog cancels the action. Typed-name matching compares trimmed strings and re-evaluates on each keystroke via StatefulBuilder.
Files
apps/flutter_app/lib/browser/browser_workspace.dart (_versionsView, _toolsView, new _confirmDeleteAll)
Verify
Widget tests: tapping “Delete selected” in Versions shows the dialog and the mock engine receives no delete until confirmed; “Delete all objects” stays disabled until the typed name matches.

G03P0ShellEffort M

A banner that knows an error from a success

Observed: AppController._guard writes failures into the same bannerMessage string used for “Listed 120 objects”. _BannerOverlay renders every message on inverseSurface and auto-dismisses after 3.5 s unless something is busy, so an error such as networkError: connection refused disappears before it can be read. Dismiss timing is chosen by matching substrings like 'listed '. Error text is prefixed with the raw enum name.

The edit
Add BannerSeverity { info, success, warning, error } and a bannerSeverity field on the controller. _guard sets error; listing/transfer completion sets success; showBannerMessage gains a severity parameter. Replace _dismissDelayFor(String) with a severity/kind switch: error = never, warning = 8 s, success = 2 s, info = 3.5 s. Map ErrorCode to human phrases.
What it does
Errors persist and are visually distinct; successes get out of the way faster; the raw enum names disappear.
How it functions
The overlay picks container colors from colorScheme.errorContainer/primaryContainer by severity, wraps the message in Semantics(liveRegion: true) so assistive tech announces it, and the Details action sets a pending Event Log filter (pairs with G14) before selectTab(eventLog).

G05P1BrowserEffort M

One object search, not two

Observed: At desktop width the header shows _HeaderSearchField (text mode only, applies on every keystroke, silently switches the filter mode to Text) while the object panel shows its own search with a mode select and Enter-to-apply. Both write objectFilterValue. The header field is keyed by bucket only, so it does not reflect a value applied from the panel. applyObjectFilter adds an Event Log entry per call, so header typing logs one event per keystroke. The panel field is keyed by the filter value, so it is rebuilt and loses focus after each submit.

The edit
Remove _HeaderSearchField; the header shows a slim button with the platform shortcut glyph that focuses the panel field. The panel field owns a TextEditingController and FocusNode in state, embeds the mode as a segmented control, debounces Text/Regex by 250 ms and applies Prefix on Enter. applyObjectFilter gains a log flag so only settled queries are recorded.
What it does
One place to search, no mode surprises, no Event Log spam, no lost focus, and a live match count.
How it functions
A Timer in _ObjectPanelState restarts on each change; focus is requested through a controller notifier (requestObjectSearchFocus()) that the panel listens to. When the controller’s filter value changes externally (breadcrumb navigation), the panel syncs the text without triggering another apply.
Files
lib/app/s3_browser_app.dart, lib/browser/object_panel.dart, lib/controllers/app_controller.dart
Verify
Widget test: typing three characters produces one filter event after the debounce; pressing ⌘K focuses the field; submitting keeps focus.
